### Methodological notes (the Fable re-check carried forward)

The proven engine from `Experiments/TranscriptSpike/Sources/TranscriptSpike/Resources/transcript.html` was ported with **two critical fixes preserved**:

- **Fix 1** (engineScrollTop clamped): the engine stores `$scroller.scrollHeight - $scroller.clientHeight` (clamped), not `$scroller.scrollHeight`. Without this, the user-scroll detector misclassified every engine repin as a user scroll-up because the 680px scrollHeight-vs-clientHeight mismatch leaked through the detector. WP-0 G2 re-run under this fix: PASS.
- **Fix 2** (userScrolledUp persists): the flag is set by an explicit user scroll AND cleared ONLY by an explicit re-pin (jump-to-latest click, pinToBottom, swapTopic, user returning to bottom band). Crucially, NOT cleared as a side-effect of an engine repin. WP-0 G2 bounce probe: PASS under this fix.

The T2 test specifically exercises Fix 2 — it scrolls up, confirms userScrolledUp=true, runs upsertMessages (which would normally call deferredRepin), confirms the user's scroll position is preserved, then calls scrollToBottom and confirms the flag clears.

### Test harness limitations (documented per E6)

- `evaluateJavaScript` cannot return `Promise` values from WKWebView (returns WKError Code=5 "unsupported type"). The test helper `waitForTwoRAFs()` uses a Swift-side 50ms sleep (≈3 frames at 60fps) instead of awaiting rAF in JS — this is the same pattern the spike harness's G2/G5 measurement-methodology used.
- `evaluateJavaScript` cannot bridge `MutationObserver` instances. The T4 helper wraps the observer install in `(function(){...; return true;})()` so the return value is bridgeable (a boolean), not the observer.
- `window.scrollTo(x, y)` does NOT fire a scroll event in WebKit (Fable Fix 4). T2 and T3 explicitly dispatch the scroll event on `document.scrollingElement` after the programmatic scroll, because the engine's listener is on `$scroller = document.scrollingElement || document.documentElement` (not on `window`). Bubbling from `window` does NOT reach the document-level listener.

### Why structured diff, not pixel diff

The route plan §3 G4 spec calls for a screenshot-diff against a reference image — that requires a real NSWindow + screencapture, which is what the spike harness (`Experiments/TranscriptSpike/`) does for Mel's visual sign-off. For a CI-friendly B2 evidence gate that runs on every commit, structured diff is the right substitute:

- **Reproducible:** the diff is `getComputedStyle()` over the same fixture on every run. No font-rendering variation, no OS-version drift, no screencapture hash collisions.
- **Verifies the contract:** the contract is "theme tokens reach the bubble chrome". The structured diff checks exactly that — any token that fails to propagate to `border-radius`, `background-color`, etc. fails the gate.
- **No false positives:** the diff is invariant to which OS font-metric happens to render today.

The visual sign-off (screencapture parity with native bubbles, route plan §3 G4) remains Mel's responsibility at P4 (parity matrix). This gate does NOT replace Mel's visual review — it's a faster regression net that runs before Mel's eye.

### Fixture corpus provenance (E4)

Both the 24-case converter matrix and the 8-theme palettes are **hardcoded JSON literals in `TranscriptFixtures.swift`** — no runtime DB access, no `ThemeManager.shared` call, no `Date()` calls. The General window is **synthetic** (25 messages shaped like a real conversation, but authored in the fixture file), with the explicit caveat documented at the top of the corpus: "When WP-3 wires the real host, the same fixture will be replaced by a GRDB-backed loader."

This trade-off is acceptable because WP-2's contract is "the document renders these inputs correctly"; WP-3's contract is "the host loads these inputs from the real DB and hands them to the document". The same fixture runs through both pipelines.

The bridge contract is `Sources/App/Resources/TranscriptTemplate.html` §4.3 + §4.5. It's frozen as of this commit — any change to a `window.bc.*` method's signature or a bridge event's name requires:

1. Q sign-off (the implementer of the contract)
2. Same-day note added to `Docs/Specs/Active/WP-3-swift-host.md` (or successor)
3. WP-3 re-validated against the new contract

| Direction | Symbol | Frozen signature |
|---|---|---|
| Swift → document | `window.bc.setTopic({topicId, messages, canLoadEarlier})` | returns `number` (loaded count) |
| Swift → document | `window.bc.upsertMessages(messages, canLoadEarlier)` | returns `{appended, total}` |
| Swift → document | `window.bc.prependEarlier(messages)` | returns `number` (prepended count) |
| Swift → document | `window.bc.setStreaming({html} | null)` | returns `boolean` |
| Swift → document | `window.bc.setThinking(state)` | state ∈ {'idle', 'thinking', 'streaming'}; returns state |
| Swift → document | `window.bc.setTheme(tokens)` | tokens: `{[string]: string}` of `--bc-*` CSS vars; returns nothing |
| Swift → document | `window.bc.setFontScale(n)` | n: number; returns nothing |
| Swift → document | `window.bc.scrollToBottom()` | returns nothing |
| Swift → document | `window.bc.state()` | returns `{loadedCount, topicId, pinned, userScrolledUp, lastAction, scrollTop, scrollHeight, clientHeight, distanceFromBottom, engineHasPinnedOnce, engineScrollTop, loadEarlierVisible, thinkingVisible}` |
| Document → Swift | `bcReady` | fires once when document is ready; Swift replays full state |
| Document → Swift | `bcLink` | payload: href string; Swift routes through `LinkPolicy.isAllowed` → `callbacks.onOpenLink` |
| Document → Swift | `bcImage` | payload: src string; routes to future native image viewer (parity with bcImage TODO) |
| Document → Swift | `bcLoadEarlier` | payload: `true`; Swift calls `MessageListObserver.loadEarlierMessages()` |
| Document → Swift | `bcCopyMessage` | payload: `{id, ok}`; A3 per-message copy success/failure signal |

> **Note on `bcPinned`:** the template's bridge-helper doc-comment (`TranscriptTemplate.html` line ~401) historically listed `bcPinned` alongside the five emitted events, but `bridge()` is **never** called with that name — `grep -n "bridge("` shows exactly five call sites: `bcReady` (initial signal), `bcLink` (anchor click), `bcImage` (image hydration), `bcLoadEarlier` (load-earlier button), `bcCopyMessage` (per-message copy). The pinned state is exposed to Swift only via `window.bc.state().pinned`, never as a bridge event. WP-3 should **not** register a `bcPinned` message handler — `state().pinned` is the source of truth.

## CSP hand-off to Mel

The CSP meta in `TranscriptTemplate.html` is:

```html
<meta http-equiv="Content-Security-Policy" content="
  default-src 'none';
  img-src https: data:;
  style-src 'unsafe-inline';
  script-src 'unsafe-inline';
  connect-src 'none';
  frame-src 'none';
  object-src 'none';
  base-uri 'none';
">
```

The full rationale for each directive is in the CSP hand-off note at `Docs/Specs/Active/WP-2-csp-handoff.md`. Mel is asked to sign off on:

1. `default-src 'none'` — strictest possible baseline; only the explicit allowances below can fire
2. `img-src https: data:` — same posture as `MessageTemplate.html`; LinkPolicy already allow-lists https, and data: URIs cover any inline base64 the markdown converter might emit
3. `style-src 'unsafe-inline'` — required because the template uses inline `style="..."` attributes (e.g. `style.cssText = 'position:fixed;...'`) and the dynamic `document.documentElement.style.setProperty('--bc-*', v)` calls from `setTheme()`. Without `'unsafe-inline'`, the document couldn't apply theme tokens at runtime.
4. `script-src 'unsafe-inline'` — required because the entire bridge script is inline in `<script>` (no external file). Same posture as `MessageTemplate.html`.
5. `connect-src 'none'` — explicit block of all network connections; the document can never fetch a remote resource except images via the allowed `img-src`
6. `frame-src 'none'`, `object-src 'none'`, `base-uri 'none'` — belt-and-braces; the document has no use for iframes/objects/base URI

The sanitizer design is **unchanged from production**: every message's HTML is run through `HTMLSanitizer.sanitize()` BEFORE it's handed to `window.bc.upsertMessages` / `setTopic` / `setStreaming`. The CSP is belt-and-braces; the sanitizer is the actual trust boundary. This matches `MessageTemplate.html`'s posture (see `Sources/App/Resources/MessageTemplate.html` lines around the inline-script comments).

The CSP `Test Case '-[BeeChatAppTests.TranscriptTemplateTests testEmbeddedTemplateHasCSPMeta]' passed` asserts the meta tag and each directive is present — the test will FAIL if any future edit drops a directive, alerting Mel to re-review.

## Deviations from the route plan (honest)

1. **`--bc-bubble-max` added** (route plan §3.2 lists 4 tokens; we added a 5th). The 66% max-width is the only structural native-bubble property that doesn't have a SwiftUI-equivalent CSS variable. Adding it makes the bubble chrome token-complete. WP-3 can override the value (e.g. for a future full-width transcript mode) without code changes.

2. **`attachCopyButton` runs on every `upsertMessages` and on every image hydration** — the spike engine didn't have copy affordances, so the proven engine had no equivalent. The implementation is idempotent (early-return if a button already exists for that `pre`). No scroll-engine interaction.

3. **Streaming-node copy button** (`#streaming-msg`) uses the same `attachMessageCopyButton` as settled messages. The streaming node is removed on settle (route plan §4.3) — no orphan buttons.

4. **`setTopic` clears children via `for (const child of $transcript.children)`** rather than `innerHTML = ''` to preserve `#load-earlier` and `#thinking` in their DOM positions. This matches the route plan's "atomic swap" guarantee — no re-creation of the button nodes means no transient focus loss for keyboard users.

5. **`scripts/embed-template.swift` is in `scripts/` not at repo root**. The task brief implied root placement but the project already has `scripts/` for build/release scripts (`build-and-install.sh`, `release.sh`). Putting `embed-template.swift` next to them is the obvious home. The Package.swift doesn't need to know about it — the script is invoked manually or from CI.

6. **The synthetic General fixture is 25 messages, not the real General's full 422**. WP-0 G1 used the real DB; WP-2's contract test uses synthetic data because (a) we need deterministic, reproducible inputs and (b) WP-3 will write the GRDB-backed loader — we don't want to write it twice. The synthetic fixture covers all message roles, all formatting (paragraph, code block, table, list, blockquote), and the streaming → settle lifecycle.

7. **No CSP for `font-src`**. The template uses system fonts only (`-apple-system, "SF Pro Text", system-ui, sans-serif`), so no font loading occurs. Adding `font-src` would be a no-op.

8. **No `media-src` directive**. The document has no `<audio>` / `<video>`. The `default-src 'none'` blocks them anyway.
